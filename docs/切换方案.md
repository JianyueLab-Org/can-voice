# 从 Mumble 切到 can-voice

这份文件回答一个问题：**语音怎么从 `can-audio` 的 Mumble 换成 `can-voice`，
而中间不出现"一半人听不见另一半"的时段。**

它是一份**待拍板的方案**，不是已经定下来的事。每一处需要人决定的地方都标着
「**待定**」。

---

## 一、两件让"平滑过渡"不成立的事实

### 1. 老客户端改不动地址

`can-audio/CLAUDE.md` 记着：Mumble 的主机名**写死在**
`client/radio.py`、`xplane_client/radio.py`、`controller/gui.py`、
`atis/gui.py`、`server/ATIS/mumble.py` 里，只有 `xpc/settings.py` 和
`msfs/settings.py` 把它当成一个可改的默认值。

所以**没有"改一行数据库就把所有人挪过去"这条路**。一个成员要用上 can-voice，
唯一的办法是**装一个新客户端**。切换的单位是"人换客户端"，不是"服务器换地址"。

can-api 的 `server` 表能同时挂两套（`audio` 和 `voice` 是两个类别），但那解决的
是**新客户端找得到新服务器**，不是把老客户端挪过去。

### 2. 两套不能跑在同一台机器的同一个端口上

Murmur 同时占 **TCP 64738 和 UDP 64738**（`can-audio/docker-compose.yml` 里就是
这么映射的），而 can-voice 的 QUIC 要 **UDP 64738**。同一台机器上第二个绑不上。

所以共存期必须**换一样**：换机器，或者换端口。

> **待定（一）**：共存期 can-voice 放哪儿？
>
> - **另一台机器 + 另一个域名**（比如 `voice.ceruleanavi.net:64738`）——干净，
>   两套互不干扰，切完直接关掉老的那台。
> - **同一台机器换端口**（比如 `audio.ceruleanavi.net:64739`）——省一台机器，
>   但两套抢同一台的 CPU 和带宽，而语音对抖动敏感。
>
> 两种都由 `server` 表里那一行承载，客户端不写死。

---

## 二、一个频率不能有两个房间

这是整件事唯一真正危险的地方。

两套同时在线时，**同一个频率会分裂成两个互不相通的房间**：一半人在 Mumble、
一半人在 can-voice，双方都以为自己在守听，而管制员叫不到其中一半。

**这比"语音完全没有"糟得多**——完全没有语音时所有人都知道要用文字，而分裂时
没有人知道自己少听见了谁。

由此得出这份方案的核心：**共存期不是过渡期，是测试期。**

- **测试期**：只有明确知情的测试者用 can-voice，他们同时开着老客户端守听，
  或者约定在无人在线的时段测。**不对外宣布"可以用了"。**
- **切换日**：一个明确的时刻，所有人换客户端。之前用新的是测试，之后用老的
  是掉队。

> **待定（二）**：切换日定在哪天，提前多久通知？
>
> 参考：每个成员都要下载并装一个新客户端，所以通知窗口至少要覆盖一个完整的
> 活动周期（大多数人一周只上线一两次）。

---

## 三、顺序

### 第 0 步：准备（现在就能做）

- [x] can-api 的 `server` 表支持 `voice` 类别
- [x] can-voice 服务端能用 compose 部署
- [ ] `voice-keygen` 生成密钥对，两半分别进 can-api 和语音服务端
- [ ] 部署语音服务端（域名 / 证书 / 放行 UDP，见 `server/README.md`）
- [ ] 四个客户端在 Windows 上打包出来

### 第 1 步：测试期（两套都在线）

`server` 表里同时有 `audio` 和 `voice` 两行。只有测试者装新客户端。

**这一阶段要验的东西，按能最早验到的顺序：**

1. 两个管制端互相听得见（不依赖模拟器）
2. 跨运营商、跨地区的抖动和丢包
3. 通播（`atis-for-can` 挂 FSD，机队出声）
4. 飞行员端（xpc / msfs），这一步要模拟器
5. 十人以上同频

> **待定（三）**：测试期要多长、要覆盖多少人才算够？
>
> 建议定一个**明确的出口条件**而不是"感觉差不多了"，否则这一期会无限延长。

### 第 2 步：切换日

1. 提前通知（见待定二）
2. 当天：`server` 表把 `audio` 那一行 `active` 置否，`voice` 留着
3. 老客户端此时仍然能连上 Mumble——**它们不读那张表**。所以要同时
   **停掉 Murmur 容器**，否则掉队的人会一直待在一个只有他自己的房间里
4. 观察一个活动周期

> **待定（四）**：切换日当天 Murmur 是**停掉**还是**留着但清空**？
>
> 停掉的话掉队的人看到"连接失败"，会去问；留着的话他会看到一个正常但空无
> 一人的频率，而那正是最难被报告的故障。**倾向停掉。**

### 第 3 步：退役（切换日之后至少一个活动周期）

- 停 `server/ATIS/` 的 Mumble 机队
- 停 Ice 认证器（`can-audio/server/login.py`）
- 拆 `fix_acl.py`、`serverconf.py` 里只为 Murmur 存在的部分
- `server` 表删掉 `audio` 那一行
- can-audio 仓库归档

**顺序不能反。** Ice 认证器是 Murmur 唯一的认证来源，Murmur 还在跑的时候停掉
它，所有人会以为是自己的密码错了。

---

## 四、回滚

切过去之后如果发现大面积不通，要能在几分钟内退回去。**前提是这些东西在整个
切换窗口里都还活着：**

- Murmur 容器（停掉但不删，`docker compose start` 就回来）
- Ice 认证器（同上）
- `server` 表里 `audio` 那一行（置否而不是删掉）
- 老客户端的下载链接（成员那边多半还留着安装目录）

> **待定（五）**：回滚窗口留多久？过了就删还是一直留着？

**回滚不需要通知每个人**——老客户端本来就没被挪走，Murmur 一回来它们自己就
连上了。这是"老客户端改不动地址"这件事唯一的好处。

---

## 五、这份方案没有覆盖的

- **CRC**：不在维护范围内。
- **网络可达性**：UDP 通不通不在这个项目的考虑范围内，P1 探针已经删掉，
  P2 Task 12（stream 回退）定为不做。如果切换日发现大量人连不上 UDP，
  那是回滚的理由，而不是一个可以当场处理的问题。
- **语音质量的主观评价**：没有基线，也没打算建。
